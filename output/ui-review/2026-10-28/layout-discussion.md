# 界面布局与容器层次访谈

状态：访谈已收敛，两轮五项设计决定均已获用户确认，复核后没有剩余产品决策分支。正式规格已发布为 [#39：修正未连接耳机页布局、传输不可用状态与选择弹窗容器](https://github.com/DOHEX/OpenRose/issues/39)，标记 `ready-for-agent`。本文是设计讨论记录，界面实现尚未修改。

## 已有约束

沿用 [ADR 0001](../../../docs/adr/0001-preserve-control-session-on-style-switch.md)、[ADR 0002](../../../docs/adr/0002-shared-kotlin-core-and-platform-adapters.md)、[默认样式规格](../../../docs/specs/ui-default-styles.md)和 [#33 页面设计记录](../2026-10-27/redesign-discussion.md)：保留 Miuix 与 Material 3 各自的默认组件观感、已有页面职责及控制会话边界。

## 第一轮已确认

2026-10-28，用户提供组件风格选择弹窗、Material 3 未连接首页和 Miuix 未连接首页三张截图，反馈“看起来很怪”，调用 grill-with-docs。用户对以下三个方向统一回答“是”：

1. **未连接宽屏布局**：采用紧凑、对齐的内容区，收紧顶部留白，扫描按钮匹配内容规模；已连接页面继续按设备信息和控制内容组织双列，未连接页面单独设计比例。
2. **容器层次**：普通说明直接排版，卡片承载完整的信息组；弹窗选项与弹窗表面协调，消除突兀的矩形底色。保留默认字体、配色和控件，修正分组与嵌套方式。
3. **平台不可用状态**：Linux 尚未实现控制传输时，首页优先解释当前限制，并提供状态详情入口。避免同时以“没有发现耳机”和禁用扫描入口暗示用户仍可通过扫描解决问题。

用户同时追问“为什么暂未实现？”。已基于桌面宿主、传输实现和项目进度解释，见下方事实记录。

## 第二轮已确认

用户对以下两项统一回答“确认”：

4. **未连接页排版**：采用居中的单列内容区，内部左对齐；说明、设备列表和操作共享清晰边界；扫描使用常规宽度按钮。
5. **传输不可用时的入口**：隐藏顶部添加按钮、附近设备空列表和扫描按钮，只显示明确原因及“查看连接与运行状态”入口。传输实际可用后才呈现完整扫描与连接流程。

## 整体方案

| 场景 | 页面结构 |
| --- | --- |
| 未连接且支持控制传输 | 两套风格均采用居中单列，内部左对齐，按连接说明、附近设备、扫描操作组织；扫描按钮使用常规宽度。窄屏随可用宽度收缩，宽屏不沿用已连接首页的双列宽度。 |
| 控制传输不可用 | 紧凑呈现真实原因与状态详情入口，隐藏不可用的添加、附近设备列表和扫描入口。Linux 当前属于这一状态。 |
| 已连接 | 沿用已有设备信息、降噪快捷操作和功能入口；保留已有宽屏双列布局及导航断点。 |
| 说明与分组 | 普通说明直接排版，卡片承载完整信息组，避免给单句说明单独套卡片。Miuix 与 Material 3 保留各自组件观感。 |
| 选择弹窗 | 选项列表与弹窗表面协调，消除明显矩形底色。继续使用库自带弹窗、单选控件、字体、形状和主题色。 |

紧凑内容区的具体最大宽度、页面边距和间距属于实施与截图复核时的布局参数，不新增用户外观设置。保持触控目标与键盘操作能力。平台不可用视图不能代替权限不足或蓝牙关闭等可恢复状态；已有可恢复状态继续提供对应操作。

默认样式规格 3.1 原先仅明确允许 Card 内的 Material 3 ListItem 使用透明背景；本轮已确认的弹窗表面协调要求需要在后续正式规格中补充对话框内选项行跟随父容器表面的规则。这是局部容器组合修正，不引入自定义配色或第三套界面风格。

默认样式规格 6.2 原先要求扫描按钮全宽；本轮 Q4 明确采用常规宽度按钮，后续正式规格和验收预期应据此替换旧规则。未连接页的内容区允许小于既有首页 1120dp 上限，已连接页双列和 680dp / 900dp 导航与布局断点继续沿用。

## 已核对事实

- 两套外壳复用 `ShellPageContent`，首页最大宽度为 1120dp；`widthIn(max).fillMaxWidth()` 的宽度约束有效。横向铺开的观感来自未连接内容沿用首页宽度、分组通铺和扫描按钮全宽，并非最大宽度约束失效。
- Miuix 分组使用 Card，单句说明与空状态因此形成细长白色容器；Material 3 分组使用平铺内容和组间分隔线。
- Material 3 弹窗使用 AlertDialog，选项使用 ListItem。当前依赖的默认弹窗容器色与默认 ListItem 容器色不同，造成截图中明显的矩形色块。
- 桌面宿主明确把传输设为不可用，并将扫描、连接和设置回调留空。界面显示的原因来自宿主提供的状态。
- ADR 0002 将 Android 设为首个交付平台，Linux / Windows 分阶段验收；[Linux #31](https://github.com/DOHEX/OpenRose/issues/31) 跟踪 Android 首版后的 i5 产品传输和读取 / ANC 控制闭环。[Windows #32](https://github.com/DOHEX/OpenRose/issues/32) 独立跟踪 Windows。2026-10-28 只读核实时，两票的验收项未勾选，均无评论提供进一步阻塞原因。
- 已有 Linux i5 研究读取证明存在可用的研究链路；它不等于 OpenRose 的 BlueZ 产品适配已经完成。当前缺口包括真实扫描 / 连接 / 订阅 / 读写接入、宿主回调接线及相应控制验收。现有记录没有说明更具体的技术阻塞。

## 设计树

- 原生组件观感、页面职责及控制会话边界：沿用已有决定。
- 未连接宽屏布局、容器层次、平台不可用状态的信息优先级：第一轮已确认。
- 未连接页单列结构、对齐与扫描按钮尺寸策略：第二轮已确认。
- 传输不可用时隐藏哪些入口与保留何种信息：第二轮已确认。
- 选择弹窗与说明容器的方向：第一轮已确认；具体布局参数留给实施与视觉复核。
- Linux 控制传输实现：独立票 #31 跟踪，本轮用户仅询问未实现原因。
- 最终复核：已完成，没有剩余产品决策分支，也没有 ADR 冲突；正式规格已发布为 #39，界面实现尚未修改。

本轮暂未出现新的领域术语，也未作出需要新增 ADR 的难以逆转的架构决定。

## 规格发布与测试边界

用户调用 to-spec 后，已明确选择“按此边界发布”：以现有公开 `OpenRoseApp` 为主要测试入口，复用合成状态、语义与键盘操作、回调观察，通过同一入口的截图与可见几何关系验证宽屏布局和弹窗表面，不新增页面或组件测试入口。

完整规格包含 36 条用户故事及实现、测试和范围约束，发布为 [GitHub #39](https://github.com/DOHEX/OpenRose/issues/39)。[本地发布正文](layout-spec-draft.md)与 GitHub 正文已逐字核对，确认票处于开放状态且 triage 标签为 `ready-for-agent`。
