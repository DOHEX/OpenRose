# 分离耳机控制、耳机流转与平台入口

> 模块布局已由 [ADR 0038](0038-rust-core-and-nsh-desktop.md) 改定；新结构接管前本文仍描述现有代码。

OpenRose 的 Android 应用、系统蓝牙进程与桌面应用消费同一套耳机能力，只有应用界面需要 Compose。重构前，FirstAngel 的沙盒按固件推导预设，漏掉了真实会话所用的游戏模式读数。沙盒为复用桌面设置段落还引入了桌面应用、两个蓝牙驱动与流转服务。我们以这些实际消费者确定模块职责。[KMP 推荐结构](https://kotlinlang.org/docs/multiplatform/multiplatform-project-recommended-structure.html)

## 决策

- `androidApp` 和 `desktopApp` 分别组装两个应用入口。`shared` 下的耳机控制、流转契约、局域网实现与界面分别编译。`platform` 下按运行平台放置蓝牙、系统音频、进程通信和集成代码。沙盒和测试夹具位于 `tools`。[模块与运行入口](../../CONTRIBUTING.md#模块结构)
- 本地会话根据型号、固件和已确认的读数推导型号能力。沙盒生成读数并复用同一规则。应用和系统入口提交类型化耳机命令，控制队列在会话内校验型号限制，按协议读回确认。均衡器曲线、触控绑定和诊断读数保留各自的领域含义。
- 耳机流转契约由手机应用、桌面和界面共同消费。Binder 与局域网传输在各自边缘编解码。远程降噪操作携带上次读取的对端、耳机与会话引用。音源设备在流转中由本机音频适配让出或接入。打开声音设置、查询本机输出由桌面直接执行。[流转行为](0017-headset-circulation.md)
- Android 应用以运行时依赖把系统模块打进同一 APK。系统模块持有自己的流转端点并使用无界面的控制代码。应用与模块的 Binder 握手版本为 7；升级时仍驻留旧版本的宿主需要重新加载系统集成作用域。所有者交接、释放证明以及系统入口可见的数据按原有进程契约执行。[单一控制会话](0011-dual-host-single-control-session.md) · [进程隔离](0018-android-module-and-platform-split.md)
- Desktop JVM 的设置段落只消费展示状态和宿主动作，沙盒与桌面应用复用该实现。应用入口持有实际托盘、系统设置与驱动。独立的 JVM 测试库供两套界面测试消费。
- 沙盒（`tools/ui-sandbox`）与桌面应用一样，以 Tao 窗口后端打开窗口（2026-11 补充）：桌面应用的 Tao 后端占有 `Dispatchers.Main`，沙盒因此依赖 `nucleus.tao` 并在 `SandboxMain` 中使用同一后端。

## 考虑过的方案

把所有源码集中在模板示例的单个共享库，会让系统宿主在编译期也能引用应用界面。只移动目录能改善导航，但沙盒仍依赖桌面驱动，界面仍需要解释跨设备消息。独立的流转契约使 KMP 的共享界面可以调用流转能力，同时让局域网实现继续使用 JVM 的网络、证书及磁盘接口。

## 后果

运行入口、共享源码、平台源码和工具有五个顶层源码目录。构建含十二个产品模块及两个开发模块。新增的流转契约和 UI 测试支持分别替代了界面层的消息编解码与跨模块读取测试源码。此决策更新 [ADR 0012](0012-shared-multiplatform-architecture.md) 的模块布局；Linux 和 Windows 仍共用一个 JVM 桌面入口。
