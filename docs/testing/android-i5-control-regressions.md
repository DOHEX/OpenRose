# 小米 14 与 EarFree i5 的 Android 控制实测

2026-11-21，在小米 14（Android 17 / API 37，HyperOS OS4.0.0.27.XNCCNXM）上测试 EarFree i5，设备读回固件 `125`。通过无线 ADB 覆盖安装当前工作树的 debug APK，沿用手机已有的设置、蓝牙配对与局域网流转配对。应用版本显示 `0.0.0-dev+bb4c110`，手机上已安装 APK 的 SHA-256 与本地产物一致，为 `8c7c852afd13490bd512c6f9545ff7129496c623480bd4e0fef4a0a3e69d5725`。系统蓝牙宿主与应用通过了身份校验，界面没有提供宿主已加载模块的独立构建哈希。

| 操作 | 实际观察 |
| --- | --- |
| 手机通过快捷面板操作 Linux 持有的 i5 | Android 的经典音频和 LE 均断开。快捷面板显示 Linux 为音源，左右耳各 100%，充电盒未知。点通透后读回通透，再点抗风噪后读回抗风噪。 |
| 将快捷面板切入后台 | 在 Linux 流转服务端口各观察 10 秒。面板可见时出现 3 个新的 TCP 对端连接，退回手机桌面后为 0。本次只统计连接次数，未测量耗电。 |
| 从手机主页点「接回手机」 | Linux 的经典与 LE 链路均释放，原默认输出保持不变。Android 报告经典与 LE 均连接，状态页显示「已连接 · i5 ZT」和 BLE 控制传输。 |
| 在普通控制和模块控制下分别写降噪模式 | 两种方式的诊断均记录 `#1 通透 · 已确认`、`#2 抗风噪 · 已确认`。当前所有者随方式分别显示为 `io.github.dohex.openrose` 与 `com.android.bluetooth`。普通 → 模块 → 普通的正常交接均达到所有者就绪、i5 已连接。 |
| 向冷启动的应用传递 i5 地址 | 模块控制下先断开应用控制，保留系统音频。确认应用进程已结束后，通过公开的 `SHOW_HEADPHONES` Activity 入口传入已配对 i5 的地址。ADB 报告冷启动、应用 PID 改变。主页先显示 i5「正在建立蓝牙连接」，单独释放此时 Linux 持有的 LE 后，状态页显示「已连接 · i5 ZT」和 BLE，全程没有在应用中另点连接。本次只有一副耳机，未从融合设备中心卡片实际点击。 |
| 已连接时切换 Miuix → Material 3 Expressive → Miuix | 每次选择后仍在个性化页，并能读回所选风格。往返前后在耳机原始记录中读到相同的控制会话编号 `4294967298`。 |
| 在添加耳机连接途中横竖屏切换 | 点选扫描到的 i5，竖屏画面显示「正在连接所选耳机」「正在订阅状态通知」。系统事件记录了两次 `MainActivity` 销毁、创建、恢复，应用 PID 不变。横屏自动进入已连接主页，回到竖屏仍显示左右耳各 99%，期间没有再次点连接。 |

旋转测试的第一次尝试保留了连接请求，随后提示「蓝牙连接或读取超时」。当时手机持有经典音频，Linux 仍有一条 LE 链路。通过 BlueZ 单独释放 Linux 的 LE 后，在手机原地重试成功。随后在 Linux 两条链路均已释放的条件下完成了表中的旋转复测。

结束时通过桌面托盘面板的「接到这台电脑」接回 i5。Linux 的经典音频与 LE 均连接，媒体传输空闲，系统默认输出与测试前相同。手机的两条蓝牙链路均释放，快捷面板从 Linux 读到左右耳各 97%、抗风噪。手机保持 Miuix、模块控制、锁定竖屏，已返回启动器。音频归属根据系统链路核对，本次未进行听音验收。

上述写入覆盖通透与抗风噪两项，以及耳机回读。其他设置、断电后的持久化、交接中途进程异常退出、LSPosed 热重载拒绝和其他手机／型号仍需各自验收。

## Linux 让出后重新占用 LE 的复现

同日用同一台小米 14 和同一副 i5 复查。CachyOS 使用 BlueZ 5.88。两端均保留 OpenRose 局域网流转配对，电脑默认输出为模拟音频。

| 操作 | 时间线与结果 |
| --- | --- |
| 旧桌面版持有耳机，从手机点「接回手机」 | Linux 先移除媒体传输，再断开 BR/EDR 和 LE。LE 断开后 2.605 秒，Linux 又建立了一条 LE 连接，电脑没有媒体传输。BlueZ 报告远端的 LE 角色为 `peripheral`，即连接由电脑发起。手机取得经典音频，但 38 秒内没有进入控制就绪状态。 |
| 正常退出旧桌面版，保持手机的经典音频 | 单独断开电脑 LE 后约 1.33 秒又连回。电脑仍受信任时，对整副耳机执行 `Device1.Disconnect`，约 2.62 秒又连回。两次回连时桌面应用均已退出。 |
| 诊断时临时撤下 i5 的电脑端信任再断开 | 在这次对照里电脑停止回连，手机控制恢复。随后电脑上原有的经典蓝牙配对消失。得到用户同意后，通过系统蓝牙重新配对，确认经典蓝牙已配对、密钥已保存、设备受信任。手机的配对保留。 |

BlueZ 5.88 默认优先使用最近建立的传输。已建立经典链路后再连接 LE，会将设备加入自动回连列表。反过来，先建立 LE 再建立经典链路，会让 BlueZ 将设备移出该列表。旧桌面版先接入 A2DP，再随音频建立 GATT 控制链路，让出时只等到经典音频断开就可以回执。[BlueZ 5.88 的传输顺序处理](https://github.com/bluez/bluez/blob/5.88/src/device.c#L3885-L3928) [BlueZ 对 LE 链路角色的定义](https://github.com/bluez/bluez/blob/5.88/doc/org.bluez.Bearer.LE.rst)

对照操作还触发了另一条可能导致配对丢失的路径。最后断开的 LE 链路本身未配对，如果断开瞬间设备不受信任，BlueZ 会把整个双模设备标记为临时设备。恢复信任不会解除这个标记，之后可能清理同一设备上保存的经典配对。正式修复全程保留信任和配对。[断开事件处理](https://github.com/bluez/bluez/blob/5.88/src/adapter.c#L9062-L9079) [临时设备判定](https://github.com/bluez/bluez/blob/5.88/src/device.c#L7550-L7563)

修改接管顺序后，在同一副耳机上还验证了两个容易误判为成功的时序。

- Linux 先建立 LE，1.59 秒后完成服务解析。在这个间隙发起 A2DP，BlueZ 可能返回 `InProgress` 而没有排入音频连接，单纯等待媒体就绪会超时。桌面现在只重试这种明确的忙响应，最多等待 10 秒；请求已受理后只观察媒体传输。[BlueZ 的 ConnectProfile 忙分支](https://github.com/bluez/bluez/blob/5.88/src/device.c#L2831-L2849)
- 双链路已连接时，对整机执行一次 `Device1.Disconnect`，实测媒体与经典链路先断，LE 留在电脑上，手机显示 D-Bus 调用未获回复。BlueZ 移除任一链路时会清掉共用的延迟断开计时器。桌面现在通过各自的 bearer 接口让出活跃链路，再检查同一副耳机在各适配器上的媒体和链路状态。旧版 BlueZ 只有聚合状态时沿用整机接口。[整机断开计时器](https://github.com/bluez/bluez/blob/5.88/src/device.c#L2074-L2146) [链路移除处理](https://github.com/bluez/bluez/blob/5.88/src/device.c#L4052-L4080)

### 修复后的双机验证

桌面侧用原有的局域网配对和真实 `DesktopRuntime`。自动化未能激活桌面托盘按钮，改由临时命令行入口调用该按钮使用的 `CirculationClient.pull`。手机实际操作 OpenRose 页面。验收期间没有手工断开 Linux 的 LE，也没有切换蓝牙信任状态。

| 起始状态 | 操作与结果 |
| --- | --- |
| 电脑已按旧版顺序接管，经典比 LE 早 5.443 秒建立 | 在保留两条连接的情况下换成修复版，再从手机点「接回手机」，约 9.6 秒控制就绪。手机仅断开控制、保留音频的 18 秒窗口内，观察到 Linux 发起两次 LE 回连，修复版分别在约 0.26 秒和 2.36 秒后自动断开。手机点一次「连接」，约 6.1 秒恢复控制，电脑两条链路均断开。 |
| 手机持有 i5，由修复版电脑正常接管，再由手机接回 | Linux 先建立 LE，0.652 秒后建立 BR/EDR，随后出现 A2DP 媒体传输，电脑控制会话就绪。手机点一次「接回手机」后约 8.1 秒控制就绪。随后退出电脑端 OpenRose，手机断开控制、保持经典音频，连续 32 秒没有 Linux LE 回连。点一次「连接」，约 5.4 秒恢复控制。 |
| 复查最初超时的添加耳机和屏幕旋转步骤 | 电脑端应用保持退出。从手机「添加耳机」重新扫描 i5，点连接后转横屏，再转回竖屏。系统记录两次 Activity 销毁与重建，应用进程保持同一个。横屏和竖屏都显示已连接、左右耳各 93%。Linux 的两条链路始终断开。 |
| 正常桌面 GUI 启动后从手机实际接回 | 通过 `:desktopApp:run` 启动工作树桌面端，托盘确认 i5 已连接、抗风噪，左右耳各 93%。手机点「接回手机」后约 10.4 秒控制就绪。Android 报告 BR/EDR 与 LE 均连接，Linux 两条链路均断开。 |

本轮最终测试的 Linux 传输 JAR SHA-256 为 `93f01d93aa39a7d1257c1938ecca70d0874801da99ce4cda65e9a0a6eef9abd8`。重配后的 Linux 经典配对和信任在各轮均保留。复测通过两端链路、媒体传输和耳机状态读回核对，未进行听音验收。

结束时电脑已重新接回 i5，正常桌面应用在托盘运行，系统默认输出与开始时一致。手机快捷面板读回电脑为音源、左右耳各 93%、抗风噪，随后返回启动器并保留模块控制和竖屏锁定。
